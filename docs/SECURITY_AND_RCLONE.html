Q-Flash Web — Bảo mật asset & Cấu hình rclone

Tóm tắt dễ hiểu cho 3 thứ đang trộn vào nhau: lỗi đang gặp trust chain Ed25519 setup rclone trên máy.

1 Lỗi đang xảy ra trên UI

Khối lỗi dài dằng dặc đỏ rực ở giữa màn hình thực ra là một ZodError được serialize thành JSON. App bị ném lỗi khi parse manifest.json tải về từ R2.

Browser fetch manifest.json trên R2
→
Zod parse với schema MỚI (v2)
→
Manifest CŨ (v1) thiếu field
chip, family, efispUnlockFile

Nói cách khác: code đang chạy schema mới, nhưng asset bundle ngoài R2 vẫn là bundle cũ. Hai bên không khớp → validate fail → UI lock ở "Kiểm tra ban đầu" với khối lỗi đỏ.

Schema cũ (đang nằm trên R2) so với schema mới (đang trong code)

v1 — manifest đang deploy

  • id, name, product
  • ablFile
  • ftdPackage
  • unlock { gptBoth4, bootImage }
  • finalGpt[6]
  • edlAbl?

v2 — schema sau commit f7bec89

  • id, name, product
  • family (discriminator: legacy-ftd | efisp-8e-gen5)
  • chip (8E | 8G2 | 8G3 | 8SG3 | 8SG4)
  • ablFile, ftdPackage, finalGpt[6]
  • unlock.payloadFile / enneaFile / finalGptFile (per-device)
  • adbExploit { exploitFile, suFile }
  • — hoặc — efisp-8e-gen5 với efispUnlockFile
Mỗi entry trong manifest cũ thiếu cả nhánh A (legacy-ftd có chip) và nhánh B (efisp-8e-gen5 có family+efispUnlockFile) → Zod đẩy ra mảng errors kép cho từng index. Đó là lý do lỗi lặp đi lặp lại 6 model nhân với 4 thông báo phụ.

2 Vì sao có "vấn đề bảo mật" — Trust chain Ed25519

Site là static, asset (ROM/ABL/payload) tải về không qua origin của bạn mà qua Cloudflare R2 + custom domain xiaomi.choimaytau.com. Nếu attacker chiếm được R2 hoặc DNS của domain đó, họ có thể thay file boot.img bằng file độc → người dùng flash vào máy thật là hỏng.

Để chặn kịch bản đó, repo này có một chuỗi tin cậy Ed25519:

Build server (offline)
→
Private key Ed25519 (PEM) chỉ tồn tại ở chỗ build, đặt trong env ASSET_SIGNING_KEY_PEM. Không bao giờ commit, không upload R2.
Khi build asset
↓
Ký detached signature cho mọi file JSON quan trọng:
manifest.json.sig · sha256sums.json.sig · flash-plan.json.sig
Paid unlock keys stay backend-only via PAYMENTS_ASSET_KEYS_PATH; do not publish keys.json.
Upload R2
↓
Cả file gốc và file .sig được rclone push lên cùng prefix release.
Browser người dùng
↓
Public key Ed25519 được nhúng vào bundle Vite qua VITE_ASSET_PUBLIC_KEY (SPKI base64). Khi tải manifest.json, browser cũng tải manifest.json.sig rồi gọi crypto.subtle.verify("Ed25519", ...).
Nếu chữ ký sai
✗
App throw WorkflowError("ASSET_SIGNATURE_INVALID") và không cho flash. Source: src/domain/assetTrust.ts:88.

Cơ chế này nằm trong commit 0b144ed feat(security): add Ed25519 asset trust chain, terminal gates, and infra hardening.

Quan trọng: nếu bạn build asset mà ASSET_SIGNING_KEY_PEM trống và VITE_ASSET_PUBLIC_KEY đã được set ở client, thì asset sẽ thiếu file .sig → browser ném ASSET_SIGNATURE_MISSING. Hai env này phải đi cùng nhau (bật cả hai, hoặc tắt cả hai).
Tại sao Ed25519 thay vì hash thường? SHA-256 chứng minh file không bị sửa so với một bản tham chiếu; nhưng nếu attacker thay luôn cả sha256sums.json thì hash kiểm tra cũng bị giả. Chữ ký bất đối xứng (Ed25519) khoá private nằm OFFLINE, attacker chỉ chiếm được R2 cũng không tạo nổi .sig hợp lệ.

Tóm tắt 3 lớp bảo mật của asset

LớpFileBảo vệ chống điều gì
L1 hash sha256sums.json R2 trả file lệch byte (mạng lỗi, cache hỏng)
L2 Ed25519 *.sig Attacker chiếm R2 / domain / man-in-the-middle
L3 mã hoá payload *.enc + backend key store Người ngoài tải thẳng từ R2 cũng không dùng được payload; key/iv chỉ cấp qua backend sau khi pass được xác thực.

3 Để sửa lỗi cần làm gì (gốc rễ)

Phải build lại bundle asset với schema mới rồi upload lên R2 release mới rồi build lại site với VITE_ASSET_BASE_URL trỏ vào release mới.

Để làm được, máy này cần đủ 5 mảnh ghép:

  1. rclone đã cài và có remote r2.
  2. R2 API token (Access key + Secret key) từ Cloudflare R2.
  3. Ed25519 keypair: private PEM (server) + public SPKI base64 (client).
  4. firmware-source/ được populate đầy đủ binary (ABL, payload, ennea, efisp...).
  5. FTD packages root (~25-40 GB .rar) — script build sẽ giải nén bằng UnRAR.

Hôm nay làm trước mảnh 1 (rclone) — sau khi xong bạn cho mình biết, mình hỏi tiếp về 2/3/4/5.

4 Cấu hình rclone trên máy bạn

Hiện tại rclone chưa có trong PATH. Các bước dưới đây làm từ đầu cho Windows 11 + PowerShell.

  1. Cài rclone

    Cách nhanh nhất là dùng winget (đã có sẵn trên Windows 11):

    winget install Rclone.Rclone

    Sau khi xong, mở PowerShell mới rồi kiểm tra:

    rclone version

    Phải in ra rclone v1.6x.x trở lên. Nếu PATH chưa được nạp lại, đóng và mở lại VS Code/Terminal.

    Không có winget? Tải zip từ https://rclone.org/downloads, giải nén vào C:\Tools\rclone\, rồi thêm vào PATH bằng System Properties → Environment Variables.

  2. Lấy R2 API Token trên Cloudflare

    1. Đăng nhập https://dash.cloudflare.com → menu R2 → Manage R2 API Tokens.
    2. Bấm Create API token → đặt tên q-flash-web-rclone.
    3. Permission: Object Read & Write.
    4. Apply to specific buckets: chọn unlockxiaomi (theo docs/ASSETS_R2.md).
    5. Bấm Create. Cloudflare hiện ra 4 thứ:
      • Access Key ID
      • Secret Access Key
      • Endpoint (dạng https://<account>.r2.cloudflarestorage.com)
      • Jurisdiction-specific endpoint (bỏ qua, dùng cái thường)
    6. Copy 3 giá trị đầu vào ghi chú tạm. Cloudflare chỉ hiện secret 1 lần.
    Endpoint mong đợi của repo này là https://e807dd1d066d407f04a0801053636a3a.r2.cloudflarestorage.com. Nếu Cloudflare cho bạn endpoint khác, nghĩa là bạn đang ở account R2 khác — phải xác nhận lại với chủ project trước khi tiếp tục.

  3. Tạo remote rclone tên r2

    Chạy:

    rclone config

    Khi tool hỏi, nhập theo bảng dưới:

    Câu hỏiTrả lời
    e/n/d/r/c/s/q?n (new remote)
    namer2
    Storages3 (Amazon S3 compliant)
    providerCloudflare
    env_authfalse (Enter để chọn 1 — Enter access key)
    access_key_idAccess Key vừa tạo ở bước 2
    secret_access_keySecret Key vừa tạo ở bước 2
    regionĐể trống (Enter)
    endpointhttps://e807dd1d066d407f04a0801053636a3a.r2.cloudflarestorage.com
    location_constraintĐể trống (Enter)
    aclĐể trống (Enter — R2 ignore ACL)
    Edit advanced config?n
    Keep this "r2" remote?y
    Quit config?q

  4. Smoke test remote

    Liệt kê file ở release production hiện tại — không sửa gì cả, chỉ list:

    rclone lsf r2:unlockxiaomi/xiaomi-webusb/releases/20260506-001 --max-depth 1

    Phải in ra danh sách dạng:

    manifest.json
manifest.json.sig
sha256sums.json
sha256sums.json.sig
abl/
firehose/
unlock/
packages/
efisp/

    Nếu bị 403 Forbidden: token sai permission hoặc sai bucket. Nếu SignatureDoesNotMatch: secret bị copy lệch (thường có khoảng trắng đầu/cuối).

  5. Cập nhật .env.local

    Mở .env.local và thêm/giữ các biến này (giá trị production):

    VITE_ASSET_BASE_URL=https://xiaomi.choimaytau.com/xiaomi-webusb/releases/20260506-001

R2_BUCKET=unlockxiaomi
R2_REMOTE=r2
R2_ASSET_DOMAIN=https://xiaomi.choimaytau.com
R2_RELEASE=20260506-001
R2_PREFIX=xiaomi-webusb/releases/20260506-001
R2_SOURCE_DIR=dist-assets
R2_VERIFY_ORIGIN=https://unlock.choimaytau.com

    Khi đến lúc release bundle mới, mình sẽ bump R2_RELEASE, R2_PREFIX, và VITE_ASSET_BASE_URL sang ngày mới (ví dụ 20260618-001). Lúc đó tạo prefix mới song song để rollback dễ.

  6. (Tuỳ chọn) Lưu credential ở chỗ khác

    rclone mặc định ghi config (kèm secret) vào %APPDATA%\rclone\rclone.conf. Nếu bạn muốn mã hoá file đó, chạy rclone config rồi chọn s (Set configuration password). Sau đó mỗi lần chạy script sync, rclone sẽ hỏi mật khẩu — hoặc set env RCLONE_CONFIG_PASS.

5 Sau khi rclone OK — bước kế tiếp

Khi smoke test ở bước 4 in ra danh sách file trên R2, nói cho mình biết kèm output thật. Sau đó mình sẽ hướng dẫn 4 mảnh còn lại theo thứ tự:

  1. Tạo Ed25519 keypair (private PEM cho build server, public SPKI base64 cho client).
  2. Populate firmware-source/ — script scripts/populate-firmware-source.ps1 đọc từ vài root path local. Cần xác nhận trên máy bạn có những root nào.
  3. Trỏ --ftd-packages-root vào kho .rar (mặc định ..\Unlock_8E_Xiaomi\Unlock_8E_Xiaomi\Goi_ha_cap).
  4. Build & sync & verify & deploy theo docs/ASSETS_R2.md + docs/DEPLOY.md.
Tới lúc đó cả 5 mảnh ghép đã đủ, một lần chạy npm run build:assets + npm run sync:assets:r2 + redeploy site là khối lỗi đỏ trong screenshot biến mất.

File này tự sinh để giải thích — không ảnh hưởng build/deploy. Đặt ở docs/SECURITY_AND_RCLONE.html.
